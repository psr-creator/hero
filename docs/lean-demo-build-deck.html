The reframe

What we cut, and why the demo gets stronger

The v1 spec was a platform. This is a sales instrument. Everything that cannot be shown in nine minutes has been removed — including things that were genuinely good ideas.

Cut from the demo

  • ERP integration — the one thing that breaks in a sandbox and cannot be fixed in the room
  • Automatic event matching — needed timestamps we no longer pull
  • Weight-validated four-level cascade — replaced by publishing a questionnaire down the org tree
  • Scorecard objects — a questionnaire is the scorecard
  • Versioning, audit export, escalation SLAs — real requirements, wrong stage

Kept, because it is what wins

  • Hierarchy publishing — one questionnaire, many divisions and departments, in one action
  • Three real workflows — publish, respond, approve with send-back
  • Cross-dependency — now a parameter on the question master, not an engine
  • 1–5 weighted scoring — the arithmetic every HR head already understands
  • Three levels of report — individual, department, division
Say this in the meeting

"Phase 1 is manual capture, because that is how your appraisal runs today and it lets us go live in weeks. Phase 2 replaces the manual entry on specific KPIs with data pulled from your ERP — same screens, same scores, the number just arrives by itself."

That framing turns the missing integration from a gap into a roadmap, and it is true.

Slide 2The removed items go on the phase 2 slide, not in the bin. A visible roadmap is worth more than a bloated demo.

Information model

Master, transaction, report

Your three-tier model holds up. Masters are set up once by an admin. Transactions are what happens every cycle. Reports read transactions and never store anything of their own.

One field you did not mention, and must not forget

Appraisal cycle belongs in the masters. Every transaction carries cycle_id. Without it you cannot run June and December separately, cannot compare cycles, and cannot re-publish next period without wiping the last one. It is one column now and a rebuild later.

Slide 3Reports are views, not tables. If the developer creates a "score master", the model is already wrong.

The one validation worth building

A questionnaire cannot be set ACTIVE until its question weights total exactly 100. Show a live counter in the builder — "Weight allocated: 85 / 100" in red until it balances. It costs an hour, and in the demo it is the moment the client realises the system is doing the thinking. Let them watch you try to save at 85 and be refused.

Slide 7Cross-dependency as a master parameter — exactly as you specified — and it costs one checkbox plus six fields.

The differentiator

Dependency without a single integration

We lost the ERP timestamps, so we can no longer prove a delay automatically. We do not need to — the provider's own appraisal score is the evidence, and it is already in the system.

adjusted = raw + ROUND( impact_share_pct ÷ 100 × ( 3 − raw ) )   capped at +2 bands, never above scale_max
1 + ROUND( 0.80 × ( 3 − 1 ) ) = 1 + 2 = 3   Payroll Manager restored from "Below" to "Meets"
Trigger condition — build exactly this

Show the alert when the consumer's rating is below 3 AND the provider's rating on the linked question is below 3, in the same cycle. Nothing adjusts automatically: the approver clicks Apply relief, types a reason, and the adjusted rating is stored alongside the raw one. The provider's scorecard gets a "1 downstream impact" flag. Never deduct from the provider — they already scored 1 on their own question.

Transaction 1 · S5

Publish run

One admin action that creates many appraisals. This is where "publish across divisions and departments" actually happens, and it must feel like one click.

Screen behaviour

  1. Select cycleDropdown, OPEN cycles only.
  2. Select questionnaireACTIVE only, weights balanced at 100.
  3. Choose targetsMulti-select divisions, then multi-select departments, then optionally designations. All three are filters, not mandatory.
  4. PreviewGrid of matched employees with their manager. Admin can untick individuals. Show the count prominently: "14 employees matched".
  5. PublishCreates one appraisal row per ticked employee at status PENDING EMPLOYEE. Confirmation shows the count created and skipped.

Transaction 2 · S6

My appraisal — employee entry

The screen the client's 400 employees will actually use. It should look like a form someone can finish in six minutes, not a system.

Layout

  • Header strip: employee name, cycle, questionnaire, status pill, weight-complete indicator
  • One row per question: text · target · weight · rating selector 1–5 · comment box
  • Rating selector as five clickable buttons, not a dropdown — it reads as a product
  • Running self score in a sticky footer, recalculating as they click
  • Two actions: Save draft and Submit for approval

Dependency claim

  • On a question where is_dependent is true, show a small link: "This KPI depends on HR Executive — raise a dependency note"
  • Opens a single text box. Stored on the answer row. Appears to the approver.

Validation on submit

RuleMessage
All questions rated"3 questions still unanswered"
Comment where evidence_required"A comment is required on Q4"
Status must be PENDING EMPLOYEE or SENT BACKscreen is read-only otherwise
Cycle must be OPEN"This cycle is closed"
On submit

Set status = SUBMITTED, stamp submitted_on, compute and store self_total, and write a row to approval_log. The appraisal now appears in the manager's inbox. Screen becomes read-only.

Slide 10Do not build file upload. A comment box is enough evidence for phase 1 and saves two days.

Transaction 3 · S7

Approval — where the demo peaks

Same grid as the employee screen, plus a manager rating column, plus the dependency alert. Build this screen last and best.

ElementBehaviour
Inbox listAll appraisals where approver_emp_id = logged-in user and status = SUBMITTED. Columns: employee, department, questionnaire, self score, submitted on, a red dot if any dependency alert fires.
Review gridQuestion · target · weight · self rating (read-only) · self comment · manager rating 1–5 · manager comment. Manager rating defaults to the self rating so the manager only changes what they disagree with.
Dependency alertAn inline banner on the affected question: "KPI-PR-01 depends on KPI-HR-01 held by Fatima A. (HR Executive), who scored 1 this cycle. Employee note: 'attendance data was late in Feb and May.'" with one button: Apply relief → 3.
Apply reliefOpens a reason box (mandatory, 20 characters). Writes adjusted_rating and adjustment_reason. Shows the raw rating struck through beside the new one — visible, never hidden.
Send backMandatory reason. Status → SENT BACK. Employee's screen reopens with the manager's reason at the top.
ApproveComputes manager_total and final_score from adjusted ratings where present, sets final_band, status → APPROVED, stamps approved_on. The scorecard report goes live.
Approval logEvery action appended: log_id, appraisal_id, action, by_emp_id, from_status, to_status, remark, timestamp. Render it as a simple timeline at the bottom of the review screen — it takes an hour and makes the system look mature.
Do not skip this

The manager rating defaulting to the self rating is a two-line change that transforms how the screen feels. Without it the manager faces 8 empty dropdowns and the demo drags. With it, you change one number, apply relief on another, and approve — eleven seconds.

Slide 11One approval level only. Manager approves, done. Two-level approval is a phase 2 line item.

Workflow

Five statuses, one loop

The whole workflow. If a developer proposes a sixth status, ask which of the nine demo clicks needs it.

Who can do what

RoleCan
ADMINAll masters, publish runs, all reports
MANAGEROwn appraisal, approval inbox for direct reports, R1 and R2 for own department
EMPLOYEEOwn appraisal and own scorecard only

Kept deliberately simple

  • DRAFT exists only for a few milliseconds during publish — keep it so the state model reads correctly, but nothing sits in it
  • No employee acknowledgment of the final score in phase 1. It is one more status and one more screen; mention it as phase 2 and the client will nod
  • CLOSED is set by closing the cycle, not per appraisal
Slide 12Every transition writes an approval_log row. That log is the answer to "can we prove what happened?"

Calculation

Scoring — all of the arithmetic

Three formulas and one lookup table. Hard-code the band boundaries; making them configurable is a phase 2 checkbox.

per question  effective = adjusted_rating ?? manager_rating
appraisal     final_score = Σ ( effective × weight_pct ) ÷ 100   → 1.00 to 5.00, two decimals
self score    self_total = Σ ( self_rating × weight_pct ) ÷ 100   shown beside it, never used for the final
department   average of final_score across APPROVED appraisals  plain mean, no weighting
BandLabelFinal score
5Exceptional4.50 – 5.00
4Exceeds3.50 – 4.49
3Meets2.50 – 3.49
2Partially meets1.50 – 2.49
1Below expectation1.00 – 1.49
The number that closes the meeting

Seed the demo Payroll Manager so that without relief he scores 2.95 — "Meets", and with relief 3.65 — "Exceeds". Show the raw total first, pause, then apply relief and let them watch the band change on screen.

Build a small Recalculate button on the review screen so the total visibly updates. Silent recalculation on save loses the moment.

Slide 13Store final_score and final_band on the appraisal row at approval. Reports read stored values — never recompute at render time.

Seed data

Making it look alive, without getting caught

Every demo environment in enterprise software is seeded. That is normal and defensible. What is not defensible is a screen that breaks when someone clicks somewhere you did not plan for.

The rule — give this to your developer verbatim

Everything on the nine-click path is real code against a real database. Everything off it is seed data that renders correctly and is read-only.

Seeded history is a demo environment. A fake screenshot behind a button is a liability. The difference is that seeded data survives an unscripted click and a faked screen does not — and clients always click somewhere you did not plan.

Demo script

The nine clicks

Nine minutes. Build the product so this exact sequence is impossible to get wrong, then never deviate from it in front of a client.

  1. Admin → Questionnaire builder — 60sOpen the Payroll questionnaire. Change a weight so the counter reads 95 / 100. Try to save. Let it refuse you. Fix it. You have now established that the system enforces rules.
  2. Scroll to the dependent question — 45sTick open the dependency block on KPI-PR-01. Show provider question, provider designation, impact share 80%. Say: "this is set once, by HR, and it applies to everyone who ever holds this role."
  3. Admin → Publish run — 60sCycle H1-2026, Payroll questionnaire, Contracting division, HR & Payroll department. Preview shows the matched employees. Publish. "That is your whole cascade — one action, every person."
  4. Log in as employee — 90sOpen My Appraisal. Rate four questions by clicking. Watch the self score build in the footer. Add a dependency note on the linked question. Submit.
  5. Log in as manager — 30sOpen the approval inbox. The submitted appraisal is there with a red dependency dot. Open Rajesh instead — the seeded one.
  6. Review the scorecard — 60sWalk the grid. Manager ratings pre-filled from self ratings. Change one. Show the running total: 2.95 — Meets expectations. Stop. Ask: "is that the right answer for a man whose supplier was late twice?"
  7. Apply relief — 90sThe dependency banner names the provider, their score, and the employee's note. Click Apply relief. Type the reason. Watch the rating move 1 → 3 with the raw score struck through, and the total move to 3.65 — Exceeds. This is the moment.
  8. Approve, then open R1 — 45sThe scorecard renders with the adjustment visible and the approval timeline underneath. "Nothing is hidden. Every change has a name and a reason on it."
  9. Finish on R3 — 90sDivision roll-up, department averages, then scroll to the dependency flag list. "This is the report your HOD will ask for every cycle. It shows you where the organisation is actually leaking." Stop talking.

Stack

  • Whatever your team ships fastest in. This spec is stack-agnostic on purpose — the field lists and state model are the deliverable
  • One relational database. Eight tables. SQLite is genuinely enough for a sandbox demo
  • Server-rendered is fine. Do not start a new SPA framework for this
  • One sandbox URL with a login. No mobile app, no offline, no SSO

Where the days get lost

  • Generic report builders. Fixed layouts only
  • File uploads. A comment box is enough
  • Email notifications. Nobody clicks an email in a demo
  • Configurable everything. Hard-code the bands. Say "configurable" in the meeting, build it when they pay
  • Pretty CSS from scratch. Use a component library and spend the time on the approval screen
